# 16/32 路确定性链路性能比较

## 方法

运行 `make benchmark-lanes PYTHON=python`，或 `python scripts/run_regression.py`。
工具为每种并行度独立编译 LATENCY=2/20、RANDOM_STALL=0 的存储模型。
同一矩阵使用同一份 fixture（固定 seed=20261019），输出始终 ready，关闭最终结果的人工 20 周期背压。
每项启动两个独立仿真进程重复执行，要求所有计数完全一致，并逐拍校验输入、逐组核对 B golden。
共 5 种尺寸 × 2 种延迟 × 2 种并行度 × 2 次重复 = 40 次测量。

周期范围：从接受 start 的时钟沿之后，到最后一个结果被接收的时钟沿。
不含数据预装载、接受 start 的那个周期、结束后的检查周期。
LATENCY 是抽象模型参数，不是一次访存的全部耗时。

输出在 `build/reports/lane_benchmark/`：

- `comparison.md`：自动生成的周期与有效 MAC/cycle 对比。
- `results.json`：全部计数、有效/含填充 MAC/cycle、权重字节/cycle、源码和 fixture 哈希、工具版本。
- 各次执行及构建日志；失败时由现有仿真执行器生成复现记录和 VCD。

`input_beats + input_wait + input_blocked = cycles`，三项互斥。
其中 input_wait 是核心输入 valid=0 的周期，包含启动和排空，不能称为 DDR stall。
output_wait 与上述统计重叠，不能再相加。一次乘加计作一个 MAC。

N=8、K=2048 时，LATENCY=2 下有效吞吐分别为 8.000 和 10.667 MAC/cycle；
LATENCY=20 下为 3.765 和 4.267 MAC/cycle。
K=129 填充到 256，因此有效 MAC/cycle 必须按原始 K 计算，不能把零填充当作有效工作。

## 解释与下一步

在当前抽象存储链路下，32 路的优势约为 33.3% 或 13.3%，并不是把并行度翻倍就能让整体速度翻倍。
结合 RTL 可见：存储模型只有一个未完成请求，各数据拍之间经过 WAIT/SEND 状态；
weight_reader 每组单独发请求。增加并行度并未消除这些访存和控制周期。
这里的趋势是当前模型的测量结果，不能外推为真实 DDR 的性能上限。

交给 B：上述计时口径、结果表和复现入口。首次上板可继续 32 路；
后续应结合实际存储接口确认拍间隔、突发长度和请求并发，再判断预取或缓存是否值得优化。
在 FPGA 型号、综合资源和实际频率未知前，不据此断言 32 路具有更好的资源效率或最终板端吞吐。
当前没有真实模型切片、token/s、Fmax、LUT/DSP 或功耗结果。
