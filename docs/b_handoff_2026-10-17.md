## B 模块修复及原因

### activation_cache：容量判断混用了元素和 beat

原式 `load_ptr + BYTE_COUNT <= MAX_K` 中 load_ptr 是 beat 索引，MAX_K 是元素数。
在 MAX_K=8192 时装满 256 个 32 元素 beat 后，旧代码仍接受后续输入，静默丢失越界内容。
定向测试原版报 `FAIL cache accepts beyond MAX_K cycle=257`。
现在按 `load_ptr < MAX_K/LANES` 判断容量，并明确 loaded_k 加法宽度。
修复后容量测试通过。完整物理 beat 装载要求 MAX_K 至少容纳 padded_K。

### weight_reader：错误响应没有完成握手

旧代码见 rd_error 即进入 S_ERROR，且 rd_data_ready 依赖权重/激活消费者。
因此错误响应可能永远留在 memory_model 的 S_SEND 中。
未对齐地址且不提供激活的定向测试报 `FAIL error response not drained cycle=101`。
现在错误响应不依赖消费者 ready，等待 rd_data_valid && rd_data_ready 后再进入 S_ERROR。
错误仍保持 sticky，恢复仍需 reset，保持 B 原版约定。

### memory_model 与 lint

显式扩展地址/长度加法，限定数组索引位宽，移除未使用的 padded_k。
合法请求字节数已对齐，直接整除获得 beat 数，避免先加 DATA_BYTES-1 的溢出。
主机写地址先检查基地址在范围内，避免极大地址加偏移回绕。
不使用 -Wno-fatal 作为最终通过条件。最初只为复现原版问题临时使用该选项。

具体差异见 b_memory_fixes.patch（可在 B 仓库用 git apply --check 预检）。
